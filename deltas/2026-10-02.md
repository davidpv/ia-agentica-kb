# Delta 2026-10-02

Ventana: desde el viernes 25 sep 2026. Solo cambios con efecto duradero en procesos de desarrollo con IA agentica.

## 1. Higiene de instructions y gobernanza de modelos (Claude Code 2.1.283)

**Qué cambió.** Claude Code 2.1.283 (25 sep 2026) añade `/doctor prompt-audit` (alias `/checkup prompt-audit`): audita `CLAUDE.md`, skills, agentes y commands en busca de patrones de prompting pensados para modelos antiguos. En managed settings aparecen controles más finos de catálogo de modelos: `availableModelsMatch: "exact"` (solo las versiones listadas; un modelo nuevo no entra hasta aprobación explícita) y `deniedModels` (bloqueo puntual aunque el allowlist lo admitiría). Opcional para gateways internos: header `x-claude-code-prompt-id` (opt-in con `CLAUDE_CODE_GATEWAY_HINT_HEADERS=1`) para agrupar requests de un mismo prompt de usuario.

**Por qué importa.** Con AGENTS.md/CLAUDE.md ya como artefacto de gobernanza (delta 25 sep), el problema pasa de «¿qué fichero?» a «¿sigue siendo válido para el modelo actual?». Instruction bloat y reglas obsoletas degradan el harness sin que el equipo lo note. El allowlist exacto convierte el rollout de modelo en cambio de configuración revisable, no en drift silencioso.

**Implicación de proceso.** Cadencia de higiene de instructions (p. ej. al cambiar default de modelo o trimestral). Política managed: modelos nuevos = deny-by-default hasta review de seguridad/coste. Si hay LLM gateway, activar correlacion de prompt-id para métricas de coste/latencia por tarea, no solo por request.

## 2. Controles de salida y proveedor para agentes desatendidos (Claude Code 2.1.285)

**Qué cambió.** Claude Code 2.1.285 (29 sep 2026) introduce la managed setting `allowedProviders`: la máquina solo puede hablar con los endpoints listados (Anthropic API, custom/gateway, Bedrock/Mantle, Vertex, Foundry, Claude Platform on AWS, cloud gateways). Añade `CLAUDE_CODE_DISABLE_WEB_FETCH` para apagar WebFetch; en Team/Enterprise, WebFetch se retira hasta cargar la política de organización si no estaba disponible al arrancar. El sandbox exigido por admin ya no se puede relajar ni desactivar desde settings de proyecto/local (ni ampliar allowlists/reabrir denies gestionados). En 2.1.286, si existe un skill `verify`, el agente recibe guía explícita de ejecutarlo antes de commit (salvo commits solo docs/tests).

**Por qué importa.** El modo automático / operación desatendida reduce el «sí» humano por paso; el riesgo se desplaza a canales de salida (proveedor, red, fetch). Allowlist de proveedor + kill-switch de WebFetch + suelo de sandbox son controles runtime, no solo política en papel. El skill `verify` formaliza un gate determinista dentro del harness de skills.

**Caveats enterprise.**
- Cerrar WebFetch reduce inyección vía páginas, pero también la capacidad de consultar docs vivas; calibrar por sensibilidad del repo.
- `allowedProviders` es managed-only: hay que desplegarlo por MDM/managed-settings, no esperar que el desarrollador lo autoimponga.
- Verificar en Bedrock/Vertex/Foundry/CI efímero: varias capacidades de instruction/skills siguen con asimetrías respecto al canal Anthropic directo.

**Implicación de proceso.** Matriz por entorno: proveedor permitido, WebFetch on/off, sandbox floor. Repos sensibles = WebFetch off + proveedor único (p. ej. solo Bedrock). Adoptar skill `verify` versionado (build/test mínimos) como pre-commit del agente; review de managed settings como cambio de pipeline.

## 3. Progressive disclosure de skills: evidencia empírica (Workday / arXiv)

**Qué cambió.** Informe de Workday AI Research (arXiv:2609.35692, sep 2026) mide eager loading vs progressive disclosure de Agent Skills (estándar agentskills.io: frontmatter `name`/`description` siempre visible; cuerpo de `SKILL.md` bajo demanda). En producción citan >5.500 clientes con agentes en Workday (agosto 2026). Hallazgos: con bibliotecas grandes, eager loading dispara tokens, degrada retrieval y llega a overflow; progressive disclosure ahorra hasta ~82 % de tokens, mejora la tasa de skill retrieval y evita crashes por contexto, a costa de algo más de latencia (invocación extra de selección). Dejan abiertas preguntas operativas: cuántos skills cargar, qué ficheros del directorio del skill incluir, y cómo auditar skills inseguros en la biblioteca.

**Por qué importa.** El mapa base ya prefería skills con divulgación progresiva frente a system prompts monolíticos; ahora hay señal empírica enterprise, no solo docs de producto. El cuello de botella del harness deja de ser «más skills» y pasa a ser diseño de metadatos (descripciones disparadoras), tamaño de biblioteca y supply-chain de skills.

**Implicación de proceso.** Mantener `AGENTS.md` corto (orientación + punteros); detalle en skills con progressive disclosure. Presupuesto de skills por agente/repo; revisar descripciones como parte del PR del skill. Incluir skills de terceros en el mismo ciclo de review que dependencias (contenido ejecutable en `scripts/`). Medir coste/latencia/retrieval al crecer la biblioteca — no solo «¿tenemos el skill?».

## Acciones recomendadas

1. Ejecutar `/doctor prompt-audit` (o equivalente manual) sobre `AGENTS.md`/`CLAUDE.md` y skills de repos activos tras cada cambio de modelo default; limpiar patrones obsoletos.
2. Definir managed policy: `availableModelsMatch: "exact"` + `deniedModels` donde haga falta, y `allowedProviders` alineado al canal corporativo (p. ej. solo Bedrock en eu-south-2); apagar WebFetch en repos con datos sensibles.
3. Inventariar skills del equipo: migrar detalle fuera de instructions always-on; adoptar skill `verify` como gate pre-commit del agente; revisar skills de terceros como dependencias.
4. Si hay gateway LLM: correlacionar por `prompt-id` y añadir métricas de tokens/latencia/deny por tarea agentica (no solo por request HTTP).
